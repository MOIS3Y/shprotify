# Архитектура

Shprotify состоит из одного HTTP-сервера на Rust и базы SQLite. Сервер
хранит общий каталог, отдаёт аудиофайлы и ведёт личные коллекции.
Любой плеер может подключиться через [HTTP API](./api.md). Сам плеер
управляет воспроизведением и решает, как показывать библиотеку.

## Как проходит запрос

Когда плеер запрашивает список записей, модуль `api` проверяет параметры
и права, а `db` читает каталог из SQLite. Для воспроизведения клиент
выбирает файл записи. Сервер открывает его через `audio` и отдаёт исходные
байты, в том числе диапазоны для перемотки.

| Что хотите изменить | Где искать |
| --- | --- |
| Запуск, настройки, журналы или локальные команды | `main`, `app`, `cli`, `config`, `logging` |
| Маршрут, проверку прав или схему ответа | `api` и `auth` |
| Запросы, транзакции и хранение | `db` |
| Чтение файлов, теги и правила каталога | `library` и `audio` |
| Плейлисты, личную историю и рекомендации | `playlists`, `audio` и `discovery` |
| Внешний сервис, импорт или расписание | `providers`, `downloads`, `jobs` и `automation` |

`main.rs` передаёт управление приложению. Обработчики HTTP отвечают
за контракт и права, а SQL-операции остаются в `db`. Внешние запросы
и запуск инструментов выполняются за пределами транзакций.

## Сканирование и другие фоновые задания

Сканирование, поиск у провайдеров и загрузка могут занимать время.
Сервер принимает запрос, сохраняет задание и возвращает адрес проверки
статуса. Клиент может опрашивать его и показывать результат или ошибку.

Загрузчик сначала получает и проверяет файл, затем импорт фиксирует
его в каталоге. Ошибка внешнего источника остаётся ошибкой задания.
Расписания запускают те же операции через интервальный диспетчер.
Администратор отдельно включает нужные интеграции. Для тестов каталога
и плеера достаточно локальных данных.

## Что хранится в базе и на диске

Исполнители, альбомы, записи и файлы относятся к общей библиотеке.
Альбом связывает записи с позициями на дисках. У одной записи может
быть несколько аудиофайлов. Избранное и история ссылаются на запись,
поэтому замена файла сохраняет связь с прослушиваниями.

Все личные данные привязаны к аккаунту. При публикации плейлиста другие
пользователи получают право читать его, а владелец продолжает управлять
им. Плейлисты, очередь, ленты и расписания используют версии, чтобы
один клиент не затёр правку другого. ID события истории позволяет
повторить запрос после сбоя связи без дубля.

В SQLite лежат каталог, метаданные, обложки и личные данные.
Подключённая музыка остаётся в папках владельца сервера.
Импортированные загрузки хранятся отдельно, по хешу содержимого.
[Схема базы данных](./database.md)

## Как собираются сервер и сайт

Nix и crane собирают и проверяют сервер. Docker-образ использует тот же
пакет. Документация собирается отдельно как статический сайт с OpenAPI
и схемой SQLite. Инструменты сайта нужны только для его сборки.
[Документация и справочники](./documentation.md)

Shprotify предоставляет версионный API и список возможностей сервера.
Клиент остаётся отдельным приложением и работает с исходными аудиофайлами.
