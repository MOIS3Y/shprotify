# Участие в проекте

Можно начать с исправления примера, теста на найденную ошибку или
небольшого изменения сервера. Если нашли проблему, опишите версию
Shprotify, что сделали, что ожидали увидеть и что получили.
[Задачи проекта на GitHub](https://github.com/MOIS3Y/shprotify/issues)

| Что хотите изменить | С чего начать |
| --- | --- |
| Поведение сервера | Запустите локальный сервер и найдите нужный модуль. [Архитектура](./architecture.md) |
| Хранение данных | Посмотрите связи таблиц и порядок работы с миграциями. [База данных](./database.md) |
| Руководство, пример или справочник API | Запустите сайт локально. [Документация и справочники](./documentation.md) |

## Запустите сервер из исходников

Клонируйте репозиторий и войдите в его папку:

```sh
git clone https://github.com/MOIS3Y/shprotify.git
cd shprotify
```

Для сборки нужны Rust 1.99 или новее, Cargo и компилятор C для SQLite.
Установите также `rustfmt` и Clippy. Если пользуетесь Nix, войдите
в готовое окружение командой `nix develop`.
[Руководство по Nix](../guide/nix.md)

```sh
mkdir -p dev/music
test -f dev/shprotify.toml || cp examples/shprotify.toml dev/shprotify.toml
cargo run --locked -- --config dev/shprotify.toml
```

По примеру база создаётся в `dev/shprotify.db`. Для работы с каталогом
положите несколько файлов в `dev/music/` и задайте
`directories = ["dev/music"]` в существующей секции `[library]`.
Если нужен Swagger, задайте `enabled = true` в секции `[docs]`.
Папка `dev/` игнорируется Git.

Проверьте сервер из второго терминала:

```sh
curl -fsS http://localhost:3000/api/v1/health
```

Ожидаемый ответ `{"status":"ok"}`. Для локальных команд аккаунтов
передавайте тот же конфиг, чтобы команды открывали ту же базу:

```sh
cargo run -- --config dev/shprotify.toml user --help
```

## Внесите и проверьте правку

Модульные тесты живут рядом с кодом. Для поведения, которое проходит
через несколько частей сервера, есть HTTP-тесты в `tests/e2e/`. Они
запускают настоящий бинарник с временной SQLite-базой и тестовым аудио.
Обращения к внешним провайдерам заменяются локальными заглушками там,
где это нужно. Для этих сценариев достаточно локальных сокетов.

```sh
cargo test --locked --test e2e
```

Перед отправкой изменения из корня репозитория запустите:

```sh
cargo fmt --all -- --check
cargo check --all-targets
cargo test --all-targets
cargo clippy --all-targets --all-features -- -D warnings
```

Держите контракты и важные ограничения рядом с Rust-кодом в `///`
и `//!`. Если изменилось поведение для пользователя, обновите обе
языковые версии соответствующей страницы. Для нового маршрута или
миграции проверьте, нужно ли [пересобрать справочники](./documentation.md).

## Опишите вклад

В pull request укажите, какую проблему решает правка, что теперь
происходит и какими командами вы это проверили. Для исправления ошибки
полезно приложить короткий сценарий, на котором её можно было увидеть.

## CI и образы для разработки клиентов

GitHub Actions запускает `nix flake check` для pull request и пушей в
`main`. Проверки собирают сайт, сравнивают сохранённый OpenAPI с ответом
самого сервера, а описание базы с миграциями. Сайт публикуется после
успешного прогона на `main`, даже если менялся только код сервера или
файлы сборки.

Для проверки клиента на свежей сборке используйте образ
`ghcr.io/mois3y/shprotify:main`. Укажите его в `SHPROTIFY_IMAGE` в
`.env` рядом с файлом Compose. Чтобы обновить сервер, выполните
`docker compose pull shprotify` и `docker compose up -d`. Если важно
зафиксировать сборку на время тестирования, используйте образ с тегом
`sha-<полный-SHA-коммита>`. Для разработки удобно завести отдельную
папку с данными.

Dependabot раз в месяц проверяет входы Nix flake и версии GitHub Actions
и предлагает обновления в pull request.

## Публикация релиза

Укажите нужную версию в `Cargo.toml` и обновите `Cargo.lock`, если
версия изменилась. Чтобы заранее посмотреть список изменений, выполните
`git cliff --unreleased` из корня репозитория с установленным git-cliff.

Поставьте тег `vX.Y.Z` на проверенный коммит и отправьте его в
репозиторий. Для версии `0.1.0` это выглядит так.

```sh
git tag -a v0.1.0 -m "Shprotify 0.1.0"
git push origin v0.1.0
```

Actions сверяет тег с `Cargo.toml`, тестирует образ Linux amd64,
публикует версионный образ в GHCR и создаёт релиз на GitHub со списком
изменений от git-cliff. Самый новый по номеру стабильный тег также
обновляет образ `latest`.

### Настройки GitHub при первом запуске

- В **Settings → Pages** выберите **GitHub Actions** как источник.
- После первой публикации образа откройте **Packages → shprotify →
  Package settings** и задайте видимость **Public**, чтобы образ можно
  было скачать без входа в GitHub. Workflow использует встроенный
  `GITHUB_TOKEN`. Если пакет уже существует и GitHub отклоняет загрузку,
  выдайте репозиторию право записи в **Manage Actions access**.
  [Документация GitHub Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)
